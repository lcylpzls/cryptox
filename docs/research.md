# 竞品与基座调研

> 结论先行：Go 标准库提供全部加密原语，但缺少"信封格式、密钥生命周期、
> 流式分块、防误用 API"这类工程方案。cryptox 不做算法大杂烩，只封装
> 经过验证的少数方案，并与 errx / logx 家族打通。

## 调研对象

| 方案 | 定位 | 值得借鉴 | 自用场景下的短板 |
| --- | --- | --- | --- |
| Go 标准库 crypto/* | 加密原语 | 实现质量高、审计充分 | 组合决策全部留给调用者：nonce 管理、信封格式、密钥轮换、错误码均未提供 |
| age / libsodium | 成熟加密工具 | 高层信封格式、防误用设计 | 外部 CGO/独立工具链，与 Go 生态/家族错误码割裂 |
| 各家自封装 | 各项目内嵌加密 | 贴合业务 | 重复实现、标准不一、审计面分散（filex 已内嵌一套） |

## 家族现状

- filex 已内嵌分块 AES-256-GCM（64 KiB/块）+ KEK/DEK 信封 +
  版本化元数据 + HMAC-SHA256 请求签名；
- updatex 已内嵌 SHA256 流式校验 + Ed25519 清单签名校验；
- authx 已内嵌 JWT 全套算法、多密钥轮换（kid）、密码哈希与 MFA。

三个库各自实现加密/签名，是 cryptox 下沉合并的直接依据。

## 自研原则

1. **原语用标准库，方案自封装**：AES-GCM / Ed25519 / SHA256 / HKDF /
   PBKDF2 全部来自标准库，cryptox 只做组合与格式；
2. **防误用优先**：正确用法（随机 nonce、AEAD 认证、常量时间比较）
   固化在 API 内，调用者不需要也不应该自行拼装；
3. **版本化信封**：所有持久化数据自带算法/版本标识，支持轮换与升级；
4. **密钥不进日志**：错误消息与日志字段只含操作与算法，不含密钥材料；
5. **家族一致**：errx 错误码、logx 审计字段、100% 覆盖、fuzz 与负面测试。
